Projects and frameworks

For every listening process, portop looks for the project it was started from and the framework serving it, so a port reads storefront · Next.js instead of node. Each row also gets a category.

How the project is found

portop starts from the process's working directory, or from a script on its command line when the process runs from / (a service started as node /srv/app/server.js), and walks up to the nearest project manifest:

The command line refines the framework: vite, next dev, manage.py runserver, uvicorn, rails server, hugo server, python -m http.server and others are recognised even without a manifest. A Next.js project running Storybook shows Storybook on Storybook's port.

A script with no project still has a language: the interpreter that runs it (python3 serve.py, php -S, ruby app.rb, node, bash, pwsh and others), or the script's extension when a launcher starts it. A script run as ./serve with a #! line is named serve, but the system runs its interpreter, so its language is known too. A binary from go run is Go.

The walk stops at your home directory and never enters system directories. Tools that live in hidden directories, AppData, Library or an app bundle (an editor's language server, say) are not projects, and paths inside node_modules or a virtualenv count as the project that contains them.

Where it appears

The PROJECT column of the table (sortable), the process details, the web dashboard, the Cockpit page and the desktop app; project, project_root, language, framework and category in JSON. The filter matches project, framework and language, and a category name typed whole (dev) shows that category.

Turn it off with --no-projects or resolve_projects: false.

Platform notes

On Linux portop reads /proc; on macOS one ps and one lsof call cover every new process; on Windows the working directory is read from the process itself, which Windows allows for your own processes. Detection runs once per process and is cached while it lives.
